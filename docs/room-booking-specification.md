# Приложение для бронирования переговорных: проект технического задания

Статус: проект для обсуждения. Решения, обозначенные как допущения, предлагаются для первой версии и могут быть изменены до начала разработки.

## 1. Цель и границы проекта

Создать клиент-серверное приложение на основе существующей формы бронирования переговорных. Пользователи смогут бронировать комнаты в одном или нескольких офисах для одной встречи, заказывать общее оборудование, отмечать оборудование как находящееся в ремонте и возвращать его в работу. Источник достоверных данных — PostgreSQL. Браузерный интерфейс обращается только к API приложения, а API работает с базой данных. Для первой версии внешние API не требуются.

Существующая страница служит визуальной и функциональной основой, но не является работающим сервисом бронирования: сейчас она не сохраняет данные. Её проверку полей необходимо заменить или дополнить серверной проверкой. Существующие материалы QA и тесты относятся к исходной статической странице и при реализации приложения потребуют пересмотра.

## 2. Предлагаемые технологии

- Интерфейс: адаптировать существующие HTML, CSS и JavaScript, использовать браузерный Fetch API и сохранить русский язык интерфейса. Форма должна быть удобна на компьютерах и мобильных устройствах.
- API: Python, FastAPI и SQLAlchemy, миграции Alembic и PostgreSQL. Опубликовать описание OpenAPI; для тестирования API и базы данных использовать pytest.
- Среда разработки: сервисы интерфейса, API и PostgreSQL в Docker Compose, постоянный том для базы и настройки через переменные окружения. Не хранить учётные данные в системе контроля версий.
- Браузерные тесты: сохранить Python Playwright и обновить сценарии для нового приложения. Остальные существующие наборы тестов можно адаптировать отдельно.

Этот стек соответствует имеющемуся окружению Python и Playwright и позволяет не вводить фронтенд-фреймворк до появления необходимости. Браузер не подключается к PostgreSQL напрямую. API и база данных должны находиться в доверенной сети, а рабочая среда — использовать HTTPS.

## 3. Начальные справочные данные

Начальные данные добавляются явным повторяемым процессом инициализации, который не сбрасывает существующие записи и не создаёт дубликатов.

| Офис | Часовой пояс IANA | Начальный набор комнат | Начальный набор оборудования |
| --- | --- | --- | --- |
| Нью-Йорк | `America/New_York` | По одной малой, средней и большой | 2 проектора, 2 устройства громкой связи |
| Лондон | `Europe/London` | По одной малой, средней и большой | 2 проектора, 2 устройства громкой связи |
| Москва | `Europe/Moscow` | По одной малой, средней и большой | 2 проектора, 2 устройства громкой связи |
| Токио | `Asia/Tokyo` | По одной малой, средней и большой | 2 проектора, 2 устройства громкой связи |

Согласованная начальная вместимость соответствует существующей форме: малая комната — 4 человека, средняя — 10, большая — 20. Комнаты, вместимость и отдельные единицы оборудования хранятся как данные, а не как константы приложения. В дальнейшем офисы, комнаты и оборудование можно добавлять без изменения кода. Название комнаты уникально в пределах офиса; каждая единица оборудования имеет постоянный идентификатор и принадлежит одному офису.

## 4. Пользователи и доступ

Система поддерживает нескольких идентифицируемых пользователей. Для входа используются локальные учётные записи с адресом электронной почты в качестве идентификатора и паролем. Подключение к почтовым сервисам, проверка существования или владения адресом, отправка и чтение писем не выполняются. Предлагаются безопасное хеширование паролей, управляемые сервером сессии в защищённых HTTP-only cookie, защита от CSRF и ограничение частоты попыток входа. Пользователь может просматривать доступность, создавать бронирования, просматривать, редактировать и отменять собственные бронирования, задавать срок ремонта оборудования; по окончании срока оно автоматически становится доступным. Администратор управляет офисами, комнатами, оборудованием и учётными записями и может просматривать и отменять любые бронирования. Редактировать чужие бронирования администратор не может; свои бронирования он редактирует как организатор. Учётные записи создаёт только администратор; самостоятельная регистрация недоступна. Исключение — первый администратор: его адрес и пароль задаются переменными окружения при первоначальной инициализации. Повторный запуск не изменяет существующую учётную запись и не сбрасывает пароль; секреты не записываются в репозиторий или журналы. Пользователь может изменить свой пароль после входа, указав текущий пароль. Администратор может сбросить пароль пользователя и задать новый без отправки писем; восстановление доступа в первой версии выполняется администратором; внешние поставщики идентификации не входят в объём первой версии.

Все защищённые операции API требуют аутентификации и проверки прав на сервере. Личность организатора определяется по учётной записи, а не по имени или адресу, переданным в запросе. Роли пользователя и администратора согласованы.

## 5. Правила бронирования

1. Бронирование представляет одну встречу с едиными фактическими моментами начала и окончания и одной или несколькими выбранными комнатами. Для одной встречи разрешено не более одной комнаты в каждом офисе; встреча между офисами предполагает выбор комнат минимум в двух разных офисах.
2. Организатор выбирает офис, комнату и количество участников для каждого выбранного офиса. Количество — целое число от 1 до вместимости комнаты. Общее число участников равно сумме по офисам. Справочник участников, календарь и приглашения не включены в планы проекта.
3. В момент фиксации бронирования сервером начало должно быть в будущем, а окончание — позже начала. Продолжительность составляет от 30 минут до 4 часов включительно и измеряется по фактически прошедшему времени. Ограничение продолжительности согласовано: от 30 минут до 4 часов включительно. Комнаты можно бронировать круглосуточно, без ограничений по рабочим часам офисов. Встреча может переходить через полночь в любом из офисов; для каждого офиса отображаются местные дата и время начала и окончания.
4. Организатор может заказать один проектор для каждой выбранной комнаты. Для бронирования в одном офисе устройство громкой связи выделяется только по запросу организатора. При бронировании в нескольких офисах одно устройство громкой связи обязательно выделяется автоматически в каждом выбранном офисе. На каждую выбранную комнату выделяется не более одного проектора и одного устройства громкой связи.
5. Комнаты и оборудование недоступны, если уже выделены для активного бронирования с пересекающимся интервалом. Интервалы полуоткрытые — `[start, end)`: новое бронирование может начаться в точный момент окончания предыдущего. Оборудование выделяется только в пределах своего офиса и если интервал бронирования не пересекается с периодом ремонта.
6. Бронирование создаётся, только если доступны все комнаты и всё необходимое оборудование. Иначе не резервируется ничего, а API возвращает информацию о конфликте и недоступных ресурсах, не раскрывая частные сведения о чужих бронированиях. Доступность в интерфейсе предварительная; при создании сервер повторно проверяет её в транзакции.
7. Организатор может отменить своё активное бронирование только до начала встречи; то же ограничение действует для администратора. Отмена атомарно освобождает все комнаты и оборудование и сохраняет запись в истории, доступной организатору и администратору. Автоматический срок удаления истории бронирований не устанавливается. Повторная отмена идемпотентна. Организатор может редактировать своё активное бронирование только до начала встречи: время, состав офисов и комнат, число участников и оборудование. При изменении применяются все правила создания, включая обязательные устройства громкой связи. Изменения сохраняются атомарно: при конфликте или ошибке исходное бронирование и его ресурсы остаются без изменений. Проверка доступности учитывает собственные текущие выделения бронирования. Повторяющиеся встречи входят в первую версию с ежедневной, еженедельной или ежемесячной периодичностью; организатор задаёт окончание серии на выбор датой последней встречи или количеством встреч. При задании даты окончания включаются все встречи с датой в исходном часовом поясе не позднее этой даты; совпадающая с ней встреча включается. В серии может быть не более 10 встреч независимо от способа задания окончания; превышение отклоняется с сообщением об ошибке. Серия сохраняет местное время в исходном часовом поясе, выбранном организатором, при переходах на летнее и зимнее время; время в других офисах пересчитывается для каждой встречи. Если местное время хотя бы одной встречи серии не существует из-за перевода часов, создание или изменение серии отклоняется целиком, а организатору предлагается выбрать другое время. Если местное время встречи серии неоднозначно при обратном переводе часов, организатор явно выбирает одно из двух допустимых смещений для каждой такой встречи до сохранения серии. При ежемесячном повторении, если в очередном месяце нет исходного числа, встреча назначается на последний день этого месяца; в следующих месяцах снова используется исходное число. Серия создаётся целиком в одной транзакции: если хотя бы для одной встречи недоступны необходимые комната или оборудование, вся серия отклоняется и ни одна встреча не создаётся. API и интерфейс показывают даты конфликтов и недоступные ресурсы. Изменение и отмена применяются только ко всей серии; отдельно изменить или отменить одну встречу серии нельзя. При редактировании ещё не начавшейся серии конфликт хотя бы одной новой встречи отклоняет всё изменение: прежняя серия и все её ресурсы сохраняются без изменений. После начала первой встречи редактирование серии недоступно; можно только отменить все предстоящие встречи, сохранив прошедшие и текущую встречу в истории.

## 6. Часовые пояса

- Для каждого офиса задан часовой пояс IANA. Организатор вводит дату и время встречи в явно выбранном исходном часовом поясе; первоначально используется пояс первого выбранного офиса. До подтверждения и на странице бронирования показываются пересчитанные начало и окончание для каждого офиса, включая даты, названия поясов и смещения UTC.
- В API передаются однозначные временные метки RFC 3339 со смещениями. Фактические моменты сохраняются в PostgreSQL как `timestamptz`; исходный пояс IANA сохраняется для отображения и аудита. Пересечения и продолжительность рассчитываются по фактическим моментам, а не по показаниям местных часов.
- Несуществующее местное время при переходе на летнее время отклоняется, пользователю предлагается выбрать другое. Для неоднозначного времени пользователь явно выбирает смещение. Сервер проверяет, что смещение допустимо для выбранного пояса и местного времени, и использует актуальные данные IANA.
- Пример: встреча 15 января 2027 года с 15:00 до 16:00 UTC проходит с 10:00 до 11:00 в Нью-Йорке, с 15:00 до 16:00 в Лондоне, с 18:00 до 19:00 в Москве и с 00:00 до 01:00 16 января в Токио. Фактическое смещение зависит от даты.

## 7. Ремонт оборудования

Каждая физическая единица оборудования имеет собственный идентификатор. Аутентифицированный пользователь при постановке на ремонт задаёт дату и время его окончания; предлагается считать началом ремонта момент сохранения. Интервал ремонта полуоткрытый: `[начало, окончание)`. Окончание должно быть позже начала. Интервалы сохраняются как фактические моменты времени; при вводе и отображении указываются часовой пояс и смещение офиса с теми же правилами перехода на летнее время, что и для бронирований.

Оборудование недоступно для бронирований, пересекающихся с интервалом ремонта. Его можно забронировать на встречу, начинающуюся в момент окончания ремонта или позднее. При наступлении окончания ремонта оборудование автоматически считается доступным для новых выделений с учётом других бронирований и периодов ремонта; ручное действие пользователя и запуск фоновой задачи для смены состояния не требуются. Интерфейс показывает офис, тип, идентификатор, текущий статус и срок ремонта.

Постановка на ремонт отклоняется с сообщением о конфликте, если заданный период пересекается с текущим или будущим активным выделением этого устройства. Выделения после окончания ремонта не препятствуют постановке на ремонт. Для пользователей с соответствующими правами ответ содержит идентификаторы затронутых бронирований. Автоматическое перераспределение оборудования не входит в первую версию. Досрочное снятие с ремонта пользователем сохраняется: фактический конец периода фиксируется в момент действия и оборудование становится доступным с этого момента. Все изменения сроков или досрочное завершение фиксируются с указанием пользователя, времени и необязательной причины. Изменение ремонта и создание бронирования согласуются на уровне транзакций, чтобы исключить пересекающиеся интервалы.

## 8. Требования к интерфейсу

- Вход и выход из системы; отображение текущего пользователя и самостоятельная смена пароля с проверкой текущего.
- Просмотр офисов, комнат и оборудования; выбор времени и просмотр доступных комнат и оборудования в каждом офисе. Для занятой комнаты показываются занятость и имя организатора, остальные подробности чужой встречи не раскрываются. Интерфейс указывает часовой пояс и сообщает, что окончательная доступность подтверждается при отправке.
- Создание бронирования с одной или несколькими строками офисов, количеством участников в каждом офисе и выбором оборудования. Обязательные устройства громкой связи для встречи между офисами выбираются автоматически с пояснением. Ошибки проверки показываются рядом с полями, при изменении доступности выводится понятное сообщение о конфликте.
- Подтверждение и подробности бронирования со всеми комнатами, оборудованием и местным временем. Список бронирований пользователя, включая историю отменённых, и возможность их редактирования и отмены с отображением конфликтов; администратору доступна история всех бронирований. Уведомления внутри приложения в первой версии не требуются.
- Просмотр отдельных единиц оборудования, постановка на ремонт с указанием даты и времени окончания и досрочное снятие с ремонта. Показывать статус, срок и пояснение, если пересекающиеся бронирования не позволяют назначить ремонт; по окончании срока статус обновляется автоматически.
- Административные экраны для добавления офисов, комнат, оборудования и учётных записей, сброса паролей пользователей, а также отмены бронирований. Часовые пояса и вместимость проверяются. Ресурсы, связанные с историей, физически не удаляются; деактивация запрещает новые бронирования с сохранением существующих записей. Деактивация офиса или комнаты запрещена при наличии текущих или будущих активных бронирований соответствующих комнат; будущие бронирования сначала отменяются, а текущие должны завершиться. Деактивация единицы оборудования также запрещена, пока она выделена для текущих или будущих активных встреч. Проверка выполняется транзакционно одновременно с деактивацией и согласуется с параллельным созданием и изменением бронирований.
- Поддержка клавиатурной навигации, связанных подписей полей, видимого фокуса, доступных сообщений об ошибках и объявлений об изменении состояния. Пользовательский ввод отображается как текст, а не HTML.

## 9. Предлагаемая модель данных

Миграции должны задавать первичные и внешние ключи, проверки обязательных полей и индексы. Предлагаемые сущности:

- `users`: идентификатор, уникальный нормализованный адрес электронной почты, отображаемое имя, хеш пароля, роль и признак активности.
- `offices`: идентификатор, уникальное название, часовой пояс IANA и признак активности.
- `rooms`: идентификатор, идентификатор офиса, название, категория размера, положительная вместимость и признак активности.
- `equipment`: идентификатор, идентификатор офиса, тип, постоянное обозначение и признак активности. Текущее состояние ремонта определяется по интервалам ремонта и текущему времени.
- `bookings`: идентификатор, идентификатор организатора, моменты начала и окончания в UTC, исходный часовой пояс, состояние и время создания и отмены.
- `booking_rooms`: идентификаторы бронирования и комнаты, количество участников в данном офисе. Ограничение на одну комнату в офисе для одного бронирования обеспечивается сервисом и, где возможно, базой данных.
- `equipment_allocations`: идентификаторы бронирования, комнаты и единицы оборудования; комната и оборудование должны относиться к соответствующим офису и бронированию.
- `equipment_repairs`: идентификатор оборудования, моменты начала и окончания ремонта, автор, время создания и необязательная причина; хранить историю досрочного завершения и изменений срока с указанием пользователя и времени.

Интервалы выделения и признак активности хранятся в записях, пригодных для ограничений базы данных, и синхронизируются в транзакции бронирования. Нельзя полагаться только на проверку доступности в приложении. Отменённые выделения сохраняются для истории, но не учитываются при проверке активных конфликтов.

## 10. Параллельная работа и согласованность

Создание, редактирование и отмена бронирований выполняются в транзакциях базы данных. Редактирование блокирует запись бронирования и ресурсы в согласованном порядке, проверяет новые интервалы и атомарно заменяет выделения; при ошибке исходные данные сохраняются. Ограничения исключения PostgreSQL для диапазонов в записях активных выделений комнат и оборудования, использующие идентификатор ресурса и `tstzrange(start, end, '[)')`, предотвращают фиксацию пересекающихся выделений даже при параллельных запросах. Скопированные значения интервала и состояния не должны расходиться с данными бронирования; это обеспечивается явно заданной структурой базы или триггерами. Перед проверкой выделений и пересечений с ремонтом строки подходящего оборудования блокируются в согласованном порядке; создание или изменение ремонта получает те же блокировки и повторно проверяет пересечения с активными выделениями внутри своей транзакции. При необходимости изменения срока ремонта применять те же проверки. Ресурсы блокируются в определённом порядке; взаимные блокировки и ошибки сериализации обрабатываются безопасно.

Создание либо фиксирует выделение всех комнат и оборудования, либо полностью откатывается. Нарушение ограничения исключения и недоступность ресурсов преобразуются в HTTP 409. Для создания бронирования используется ключ идемпотентности, привязанный к пользователю и запросу: повтор с тем же ключом и содержимым возвращает исходный результат, а использование ключа с другими данными отклоняется. Ограничения базы остаются последним уровнем защиты и при одновременной работе нескольких экземпляров API.

## 11. Предварительный состав API

Все конечные точки расположены под `/api/v1`, обмениваются JSON и возвращают единообразные объекты ошибок со стабильным кодом, понятным сообщением и при необходимости сведениями о полях. Временные метки соответствуют RFC 3339. Для списков при необходимости используется постраничная выдача. Точные схемы запросов и ответов будут заданы в контракте OpenAPI.

| Метод и путь | Назначение |
| --- | --- |
| `POST /sessions`, `DELETE /sessions/current`, `GET /users/me` | Вход, выход и сведения о текущем пользователе |
| `POST /users/me/change-password` | Смена собственного пароля с проверкой текущего |
| `GET /offices`, `GET /offices/{id}/rooms`, `GET /offices/{id}/equipment` | Справочники и состояние оборудования |
| `GET /availability` | Доступность на интервал для выбранных офисов; для занятых комнат доступны интервалы занятости и имя организатора |
| `POST /bookings`, `GET /bookings`, `GET /bookings/{id}` | Создание, список и просмотр бронирований |
| `PATCH /bookings/{id}`, `POST /bookings/{id}/cancel` | Редактирование и отмена бронирования |
| `POST /equipment/{id}/repair`, `POST /equipment/{id}/return-to-service` | Постановка на ремонт с датой и временем окончания; досрочное снятие с ремонта |
| `POST /admin/offices`, `POST /admin/rooms`, `POST /admin/equipment`, `POST /admin/users` | Создание справочных записей и учётных записей |
| `POST /admin/users/{id}/reset-password` | Сброс пароля пользователя администратором |
| `PATCH /admin/offices/{id}`, `PATCH /admin/rooms/{id}`, `PATCH /admin/equipment/{id}` | Изменение или деактивация справочных записей |

HTTP 400 используется для некорректно сформированного запроса, 401 — при отсутствии аутентификации, 403 — при недостатке прав, 404 — для отсутствующих или недоступных ресурсов, 409 — при конфликте бронирования или ремонта, 422 — при нарушении бизнес-правил. Пароли, токены сессий и чувствительные детали ошибок базы не должны попадать в ответы или журналы.

## 13. Критерии приёмки и проверка

Реализация принимается, когда автоматизированные тесты API, базы данных и браузерного интерфейса подтверждают следующее:

1. Начальные данные содержат четыре офиса, по три комнаты и по четыре единицы оборудования в каждом; новые офисы, комнаты и оборудование добавляются без изменения кода.
2. Корректное бронирование в одном офисе сохраняется после обновления страницы и перезапуска сервера; некорректные данные и превышение вместимости отклоняются API и объясняются в интерфейсе.
3. Бронирование в нескольких офисах показывает правильные местные даты и смещения, выделяет устройство громкой связи в каждом офисе и фиксирует все ресурсы вместе. Проверены январский пример, переходы на летнее время, неоднозначное и несуществующее местное время, а также переход через полночь.
4. Смежные бронирования создаются; пересекающиеся бронирования одной комнаты или оборудования отклоняются. Параллельный тест с независимыми подключениями к базе подтверждает, что из конкурирующих бронирований успешно только одно, в том числе при конкуренции за последнюю единицу оборудования. Неудачное бронирование в нескольких офисах не оставляет частичных выделений.
5. Бронирование оборудования, пересекающееся с ремонтом, отклоняется; встречу можно забронировать с момента окончания ремонта или позднее. В момент окончания устройство автоматически становится доступным без ручного действия и фоновой задачи, если не занято другим бронированием. Досрочное снятие с ремонта также освобождает устройство. Постановка на ремонт отклоняется только при пересечении с текущим или будущим выделением; выделение после окончания ремонта ей не препятствует. Параллельные запросы ремонта и бронирования не создают пересекающихся интервалов.
6. Отмена освобождает ресурсы, после чего другой пользователь может их забронировать. Проверка прав предотвращает несанкционированный доступ и отмену; повторы с ключом идемпотентности не создают дубликаты.
7. Деактивация офиса, комнаты или оборудования отклоняется при соответствующих текущих или будущих активных бронированиях; после завершения или отмены таких бронирований она доступна.
8. Серия содержит не более 10 встреч при задании окончания как датой, так и количеством. При создании серии проверяются все встречи; конфликт любой из них отклоняет всю серию, не оставляя частичных бронирований.
9. Ожидания существующих тестов статической формы пересмотрены с учётом нового поведения; соответствующие новые наборы pytest и Playwright выполнены, результаты задокументированы.
